# CLAUDE.md

Guidance for Claude Code when working in this repository.

## What this is

C3 bindings for [Clay](https://github.com/nicbarker/clay) (single-header C UI layout library, zlib),
packaged as a C3 library (`.c3l`), not a standalone program.

- `manifest.json` provides the `clay` package for the `clay` module. `"sources": [ "src/**" ]`
  replaces the default scan of the package root: a `.c3` left at the root is silently not compiled.
  `"c-sources": [ "csrc/clay.c" ]` compiles the Clay implementation with the consumer's C compiler
  on every target (`cc` on Linux, MSVC `cl` on Windows); there is no native archive.
- `src/clay.c3i` is the raw layer: every type Clay's bound functions pass, in header order, plus
  every bound C function as `extern fn ... @cname("Clay_...")`. `src/clay.c3` is the idiomatic
  layer: `id`, `chars`, sizing helpers, `@element`, `open_element`, `configure_element`,
  `close_element`, `text` and slice views. `src/layout_posix.c3` and `src/layout_windows.c3` are
  generated by `scripts/probe-layout.sh` and never edited by hand.
- `vendor/clay/` is the upstream repository as a git submodule, pinned to a commit. Read the real
  declaration in `vendor/clay/clay.h` before writing or changing any C3 declaration; a wrong field
  or parameter type is a silent cross-ABI memory bug.
- `test/` is a standalone consumer project. `test/libs/clay.c3l` is a symlink to the repository
  root because c3c resolves a dependency as `<search-path>/<name>.c3l`. `cd test && c3c test`
  compiles the binding and runs `src/smoke.c3`.

## Authoring rules

- Invoke the `c3-expert`, `c3-style` and `c3-bindings` skills before writing, editing or
  reviewing any C3 or diagnosing a c3c error. C3 is 0.8.3 here and pre-1.0.
- Do not run `c3fmt`. Hand-format: K&R braces, four spaces.
- Docstrings on every public type, constant and wrapper in `src/clay.c3` (raw externs and layout
  types carry none): one summary line, `@param` for pointers and any parameter its name does not
  explain. No narration.
- No development vocabulary in code: no ticket references, plan steps or milestone names.

## Binding conventions

- The `Clay_` prefix is the module name, never part of an identifier: `clay::begin_layout`, not
  `clay::Clay_BeginLayout`. Functions `snake_case`, types `PascalCase`, constants and enum values
  `SCREAMING_SNAKE_CASE`, fields `snake_case`. No `@builtin`.
- `Clay_String` and `Clay_StringSlice` are `Chars` and `CharsSlice`, so C3's `String` is never
  shadowed in an importer.
- Clay's `CLAY_PACKED_ENUM` enums are one byte under gcc and clang but int-sized under MSVC's C
  compiler. They are declared over `PackedEnum`, an alias that is `int` under `@feat(WIN32)` and
  `char` elsewhere. Plain C enums (`Clay_TransitionState`) are `: int`; the flag enum
  `Clay_TransitionProperty` is `typedef TransitionProperty = uint`.
- `Clay__OpenElementWithId`, `Clay__ConfigureOpenElementPtr`, `Clay__CloseElement` and
  `Clay__OpenTextElement` are `@private` hooks behind the idiomatic layer. Opening and configuring
  are separate calls because a scroll container reads `get_scroll_offset()` between them.
- Bind only the surface a consumer uses; transitions are declared for layout and not bound further.
- The layout pins are generated per platform: after any struct change or Clay upgrade run
  `scripts/probe-layout.sh --update` on Linux and on Windows (or copy the Windows job's probed
  values into `scripts/abi-sizes-windows.txt` and run `--generate windows`), then `--check`. Pins
  cover size and alignment of every bound struct and the field offsets of the structs consumers
  read and write.

## Verification

```sh
scripts/probe-layout.sh --check
c3c compile-only --no-obj src/*.c3i src/*.c3 && rm -rf obj
cd test && c3c test
```
